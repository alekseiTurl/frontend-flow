# Frontend flow

Coordinate in Russian with the user unless requested otherwise. All authored documentation, plans, reports and commit/MR text must be in Russian unless the user explicitly requests another language; follow the language rule in common.md in every role and mode. Execute dependent stages sequentially. Skill maintenance uses skill-creator and does not start this workflow.

## Короткие вызовы

- `@FF` в прямом запросе пользователя — сокращение полного вызова frontend-flow. Запускайте или продолжайте workflow по обычным правилам планирования, согласования, разработки, ревью и writing.
- `@FW` в прямом отдельном запросе — сокращение вызова frontend_writer. Делегируйте только автору с mode=standalone; не запускайте архитектора, разработчика, багфиксера, тестировщика, ревьюера и не создавайте состояние workflow. Если пользователь не ограничил результат одним артефактом, подготовьте оба текста: сообщение коммита и заголовок/описание MR. Используйте указанные изменения или контекст текущей задачи; если область неясна, уточните её.
- Если `@FW` явно относится к этапу writing текущего frontend-flow, сохраняйте mode=frontend-flow и его требования к готовности. Сокращение не позволяет обойти проверки активной задачи.
- Это текстовые сокращения, а не переименование навыка/агента и не регистрация пунктов меню @. Прежние полные вызовы продолжают работать. Примеры, цитаты и обсуждение настройки сокращений не запускают workflow. Сокращения не разрешают создавать коммит, публиковать MR или отправлять сообщения.

## Superpowers integration

This workflow incorporates selected Superpowers practices directly: evidence-led debugging and behavior-focused test-first development in developer.md, acceptance-driven work packages in architect.md, and requirements then quality review in reviewer.md. It works without an installed Superpowers plugin. Existing roles, model routing, consent records, developer reuse, writer ownership and completion checks remain authoritative within this workflow. Do not automatically launch a second Superpowers orchestrator, bootstrap, parallel developers or per-task commit cycle. If the user explicitly invokes both workflows and their requirements conflict, explain the specific conflict before affected work; do not silently claim full Superpowers compliance.

Adapted from [Superpowers](https://github.com/obra/superpowers): systematic-debugging, test-driven-development, verification-before-completion and subagent-driven-development (consulted 2026-09-28). This is a selective adaptation, not a vendored plugin; upstream updates do not change these local rules automatically.

For normal workflow stages set mode=frontend-flow. Send compact self-contained assignments: objective, absolute project/task paths, owned scope, relevant artifact paths, decisions, approval evidence and the Russian documentation requirement. Pass file paths instead of full history, diffs or logs. Read only active-stage references. Preserve prior agents for follow-ups, reuse unchanged evidence, and communicate deltas. The coordinator owns state and reports, relays questions and records outputs; it does not duplicate implementation, review or author commit/MR text.

## Standalone review and writing

Only frontend_reviewer and frontend_writer support standalone assignments outside this workflow. When the user explicitly requests one of them separately, dispatch only that role with mode=standalone, the absolute project path, exact requested scope/comparison, available evidence and desired output. Use the same model, effort, fork_turns="none" and common rules. Do not start architecture, implementation, workflow state, approval gates or completion checks for these standalone tasks. Read the corresponding role reference for its standalone behavior. Existing workflow work remains mode=frontend-flow; missing artifacts do not justify switching modes. Architect, developer, bugfixer and tester roles remain workflow-only.

## Plan and clarify

Read [state contract](references/state.md) when creating/resuming a task. Use a unique <project-root>/.frontend-flow/<task-id>/ or the project's prescribed writable artifact directory. Record an alternative absolute path; the recovery hook discovers only the default. Keep artifacts out of deliverable diffs/commits without changing tracked ignore rules. Record baseline branch/HEAD, agreed comparison, and existing tracked/untracked source changes. Never invent a base branch. Exclude secrets from inventories, diff content and snapshots per common.md.

Reuse a relevant approved plan. Otherwise dispatch the architect to inspect relevant code, identify consequential unknowns, ask focused questions through the coordinator, and select junior, middle or senior for feature work, or frontend_bugfixer for a defect-fixing package, with a short evidence-based reason. Relay 1-3 questions at a time with a recommended choice where useful; forward answers to the same architect. Continue independent discovery while awaiting answers; do not finalize decisions dependent on required answers. Optional unanswered questions may become explicit conservative assumptions after a reasonable response opportunity. Do not ask questions already answered by the user or repository.

Save the approval-ready plan.md with version/hash, present the substantive plan including developer selection, and request explicit approval before production edits or developer/bugfixer dispatch. Cite this skill's requirement when asking. Existing user authorization can satisfy approval if it verifiably covers that exact plan; never require the user to repeat it. Save exact user text, turn reference if available, timestamp, version and SHA-256. A saved plan without verifiable consent needs approval, not replanning. Run `node <skill-dir>/scripts/check-flow.cjs check-plan <task-dir>` before development and each fix round; the script checks integrity, not consent.

Material scope/contract/architecture changes require an architect revision, incremented plan version and renewed approval unless already explicitly authorized. Routine implementation details and switching junior to middle/senior or middle to senior within the same approved scope do not require new plan approval. For an implementation escalation, ask the architect only for a delta classification, record it separately, and leave approved plan bytes unchanged.

## Implement, test UI and review

Use the architect's validation strategy for each package. Preserve the current checkout when suitable; use managed worktree tools when isolation is needed and available. Record the actual checkout and its baseline before developer dispatch. Do not assume a new worktree contains uncommitted user changes or copy them automatically. Establish the relevant test baseline, distinguish existing failures from regressions, and record blocked checks honestly. Existing required-check waiver rules still apply.

Dispatch only the selected implementer (junior_dev, middle_dev, senior_dev or frontend_bugfixer) for a work package; do not launch multiple implementers for the same scope. Give unchanged approved plan/version, approval evidence, check-plan result, baseline and explicit file/module ownership. Save implementation.md and actual checks. Blocked is not passed. On a junior or middle escalation, stop its edits, have the architect classify only remaining work, then hand scope and concise progress/blockers to the selected higher tier. Select the appropriate tier directly; do not require a junior-to-middle-to-senior sequence. Preserve attempt counts across handoffs. Preserve existing work; avoid repeated unsuccessful attempts. Different packages may use different tiers sequentially when the architect has explicitly decomposed them.

После реализации определите по плану и фактическим изменениям, затронуты ли внешний вид или поведение UI, включая тексты, формы, навигацию и состояние интерфейса. Зафиксируйте решение и причину в state.ui_testing. При изменении UI обязательно запустите отдельного frontend_tester по [инструкции тестировщика](references/tester.md) до финального ревью и writing. Передайте критерии, checkout, snapshot, команду запуска/URL, безопасные тестовые данные и каталог артефактов. Тестировщик запускает приложение или использует готовый сервер и проверяет его через Playwright MCP. Сохраните отчёт в ui-testing.md, findings — в общий ledger, а проверку playwright-ui — как required=true. Если UI не затронут, запишите required=false с причиной и не запускайте тестировщика. Недоступная проверка имеет статус blocked; независимое ревью можно продолжать, но завершение требует passed либо явного исключения пользователя.

Start a fresh independent reviewer for initial review. Supply approved plan, baseline, implementation, UI testing report when applicable, ledger, exact current comparison and relevant source inventory; the reviewer reads the live diff and applies code-review. Save review.md, stable finding IDs, evidence, priorities and statuses. The reviewer does not author commit/MR text.

Передавайте выявленные тестировщиком или ревьюером дефекты отдельному frontend_bugfixer по [инструкции багфиксера](references/bugfixer.md). Перед первым редактированием передайте ему утверждённый план, подтверждение согласования, успешный check-plan, checkout, актуальный snapshot, ID дефектов, воспроизведение и границы файлов/модулей. Исходный разработчик передаёт краткий контекст и прекращает изменения в переданной области. Не запускайте багфиксера без задачи на исправление дефекта и не добавляйте его вторым исполнителем тех же правок. Новую функциональность и незавершённые части реализации оставляйте выбранному разработчику. Смена исполнителя внутри утверждённого scope не требует нового согласования плана.

Reuse the same bugfixer, tester when UI is affected, and reviewer for subsequent fix rounds at their configured effort; send only findings, new evidence and changes since the last snapshot. Restart only if unavailable/context unusable; restore from artifacts. A reviewer must not have authored the implementation. Developers, the bugfixer and testers cannot close findings. После исправления UI тестировщик повторяет затронутые сценарии; ревьюер закрывает findings с опорой на его результаты. Disputes go to the user with both arguments; rejected_by_user needs actual user evidence. Continue uncontested fixes; do not complete with unresolved findings. After three rounds on the same unresolved defect or without meaningful progress, report the impasse. Смена исполнителя не обнуляет число попыток; багфиксер сообщает блокировку раньше, если нет проверяемой гипотезы или необходимого доступа. Scope changes return to planning.

## Write and complete

Before final verification, reconcile every acceptance criterion with the review's evidence or an explicit user-approved deviation. Verify actual check outputs and their applicability to the current source snapshot; a developer's success summary alone is insufficient. Reuse valid unchanged evidence instead of rerunning checks as a ritual. A passing lint run does not establish build, runtime or UI correctness. Для UI-изменений проверьте отчёт frontend_tester и применимость доказательств к финальному snapshot; при изменении UI повторите затронутые сценарии.

After accepted review and passing required checks (or explicit user waivers), verify the source snapshot is unchanged and set review.final_verified=true. Dispatch frontend_writer once with plan, implementation, review, checks, final snapshot and project path. Only this agent discovers commit/MR conventions/templates and authors commit-message.md and mr-description.md. Save its text verbatim and record authorship, snapshot and output hashes in state.writing. Ask it to correct inaccurate or incomplete text; other roles do not rewrite it. No separate commit-writing and MR-writing turns are needed.

Before presenting the final result and requesting completion, recheck that the reviewed source snapshot is unchanged after writing and run check-done. Any later source change invalidates final review and writing and requires reassessing UI evidence against the new snapshot; review the delta and refresh the writer against the final evidence. Drafting text does not authorize git commit, push, publishing an MR, merge, deployment or sending messages; execute such actions only within actual task authorization.

## Подтверждение завершения и очистка

Сразу после сохранения окончательных текстов commit-message.md и mr-description.md и успешного check-done удалите plan.md текущей задачи, включая созданные этой задачей временные копии и промежуточные версии плана. check-done выполните до удаления: он читает plan.md. Не ждите подтверждения завершения и не спрашивайте отдельного разрешения на удаление плана. Применяйте правила безопасной очистки ниже; не удаляйте пользовательские планы или итоговые документы. Не создавайте резервную копию удаляемого плана. Затем установите phase=awaiting_completion. Покажите в чате результат, проверки, ограничения/согласованные исключения и полный текст обоих артефактов writer без изменений: ссылки на временные файлы недостаточны, поскольку эти файлы будут удалены. Затем спросите: «Завершаем задачу и удаляем её служебные файлы .frontend-flow?» Объясните, что подтверждение нужно по этому разделу навыка, и дайте ссылку на SKILL.md. Если пользователь уже явно подтвердил завершение именно этой задачи после получения финальных текстов, повторный вопрос не нужен. До ответа сохраняйте остальные артефакты; plan.md к этому моменту уже удалён; молчание, согласование плана или разрешение на реализацию не означают завершение. При запросе доработок вернитесь к соответствующему этапу.

После подтверждения завершения сохраните подтверждение по state.md, установите phase=complete и сразу переходите к очистке. На этом этапе не проверяйте diff, snapshot, хеши кода или артефактов, не запускайте повторно check-done, тесты, ревью или writer: эти проверки относятся к работе до предъявления финального результата. Удалите все известные временные файлы, созданные при работе над этой задачей: её служебный каталог .frontend-flow, временные скрипты, логи, снимки и другие промежуточные файлы, в том числе за пределами служебного каталога. Для очистки проверяйте только принадлежность файлов задаче, безопасные границы путей и отсутствие использующих их процессов. Очистку выполняет координатор, когда агенты и процессы уже не используют каталог. Перед рекурсивным удалением разрешите абсолютные пути и проверьте, что каталог задачи является отдельным дочерним каталогом ожидаемого <project-root>/.frontend-flow, либо ранее записанного альтернативного каталога артефактов. Не удаляйте корень проекта, общий каталог артефактов, соседние задачи, исходники или пользовательские файлы; не переходите по symlink/junction/reparse points. Для смешанного каталога и временных файлов вне каталога задачи удаляйте только конкретные известные файлы, созданные этой задачей. Сохраняйте итоговые пользовательские результаты; не считайте файл временным только потому, что он untracked. На Windows используйте Remove-Item -LiteralPath в PowerShell после проверки путей. Общую .frontend-flow можно удалить только после проверки, что она пуста.

Сообщите фактический результат очистки; при ошибке сообщите оставшийся путь и причину, не заявляйте, что файлы удалены. Подтверждение завершения разрешает эту очистку, но не commit/push/MR/merge/deploy. Финальные тексты остаются в чате; не создавайте резервную копию служебного каталога без запроса пользователя. Самостоятельные review/writing задания не создают workflow-состояние и не запускают эту процедуру.

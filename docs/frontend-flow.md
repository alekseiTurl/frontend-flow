# Frontend flow — краткая инструкция

Обновлено: 8 октября 2026 года.

## Роли

| Агент | Модель / усилие | Задача |
| --- | --- | --- |
| Architect (`frontend_architect`) | `gpt-6-astra / medium` | Уточняет требования, готовит план и проверки, выбирает исполнителя |
| **Junior Dev** (`junior_dev`) | `gpt-5.6-luna / medium` | Простые рутинные правки по готовому образцу |
| **Middle Dev** (`middle_dev`) | `gpt-5.6-terra / high` | Локальная логика, взаимодействие компонентов, типовые формы и состояния |
| **Senior Dev** (`senior_dev`) | `gpt-6-sol / high` | Сложная логика, связи модулей, async, SSR |
| Bugfixer (`frontend_bugfixer`) | `gpt-6-sol / high` | Воспроизводит дефекты, устраняет причину, запускает проверки |
| Tester (`frontend_tester`) | `gpt-5.6-sol / high` | Запускает приложение и проверяет изменённый UI через Playwright MCP |
| Reviewer (`frontend_reviewer`) | `gpt-6.1-sol / high` | Проверяет выполнение требований, качество кода и исправления |
| Writer (`frontend_writer`) | `gpt-6-luna / low` | Готовит сообщения коммитов и описания MR |

## Короткие вызовы

Пишите сокращение обычным текстом в сообщении нужного проекта:

| Вызов | Результат |
| --- | --- |
| `@FF` | Полный frontend-flow: план → реализация → проверка UI при его изменении → ревью → исправления при необходимости → тексты коммита и MR |
| `@FW` | Только frontend_writer: сообщение коммита и/или заголовок и описание MR |

Примеры:

```text
@FF Добавь фильтрацию товаров. Критерии готовности: ...
@FF Исправь баг: [шаги воспроизведения]. Ожидаю: [результат]. Сейчас: [ошибка].
@FF Продолжи сохранённую задачу по фильтрации товаров.
@FW По staged-изменениям подготовь сообщение коммита.
@FW По текущим изменениям подготовь заголовок и описание MR.
@FW Подготовь сообщение коммита и описание MR по текущим изменениям.
```

При отдельном `@FW` остальные этапы flow не запускаются. Если вид текста не указан, автор готовит оба артефакта. Если `@FW` явно вызван для этапа writing текущего flow, сохраняются проверки этого этапа. Сокращения не означают создание коммита или публикацию MR.

Это текстовые сокращения в инструкциях Codex, а не отдельные пункты меню `@`. Полные вызовы `$frontend-flow` и `frontend_writer` остаются доступны. После обновления начните новый чат, чтобы загрузились новые описания навыка и роли.

## Полный процесс

В задаче нужного проекта напишите:

> Используй $frontend-flow. Нужно [задача]. Критерии готовности: [результат]. Ограничения: [условия].

1. Архитектор изучает проект, задаёт существенные вопросы и предлагает план с критериями готовности, границами работ, проверками и выбором исполнителя. Для задачи на исправление дефекта выбирает багфиксера.
2. Вы утверждаете конкретный план. Если он уже утверждён и согласование подтверждается перепиской, повторное согласование не нужно.
3. Выбранный исполнитель выполняет работу и фиксирует результаты проверок. На один пакет работ назначается один исполнитель.
4. При изменении внешнего вида или поведения UI тестировщик запускает приложение либо использует готовый сервер нужного checkout и проверяет интерфейс через Playwright MCP. Если UI не затронут, координатор записывает причину и не запускает тестировщика.
5. Независимый ревьюер сначала проверяет выполнение требований, затем дефекты и качество кода, учитывая результаты тестировщика.
6. Выявленные дефекты получает багфиксер. Он исправляет причину и запускает затронутые проверки. UI повторно проверяет тестировщик; закрытие замечаний подтверждает ревьюер.
7. После принятого ревью и успешных обязательных проверок либо явно согласованных вами исключений автор готовит `commit-message.md` и `mr-description.md` по правилам проекта. Система проверяет, что тексты относятся к проверенной версии кода.

Junior Dev получает простые рутинные правки: текст, простые стили, повторение готовой разметки или механические изменения в заданных файлах. Middle Dev — локальную логику, взаимодействие компонентов, типовые формы и состояния с понятными требованиями. Senior Dev — сложные связи модулей, async, SSR, контракты и архитектурную неопределённость. Архитектор сразу выбирает подходящий уровень; обязательной цепочки Junior → Middle → Senior нет.

Если задача выходит за рутинные рамки или одна содержательная попытка исправления не дала прогресса, Junior Dev передаёт контекст через координатора архитектору для выбора Middle Dev или Senior Dev. Middle Dev передаёт работу Senior Dev после двух неудачных попыток по одной проблеме, включая предыдущую попытку Junior Dev. Задачи на исправление дефектов и замечания после тестирования/ревью получает отдельный `frontend_bugfixer`. Разработчики, архитектор, тестировщик и багфиксер работают только внутри flow.

Багфиксер получает утверждённый план, успешный `check-plan`, ID дефектов, воспроизведение, границы файлов и результаты предыдущих попыток. Исходный разработчик прекращает правки в переданной области. Без задачи на исправление дефекта багфиксер не запускается; новую функциональность продолжают разрабатывать Junior Dev, Middle Dev или Senior Dev согласно выбранной сложности. Исправления и проверки дописываются в `implementation.md`, отдельный повтор полного исследования не требуется.

Обычные детали реализации, переход Junior → Middle/Senior или Middle → Senior и передача исправлений багфиксеру в пределах утверждённой задачи не требуют нового согласования. Существенные изменения требований, контрактов или архитектуры возвращаются к плану и согласованию, если ещё не были разрешены вами. После трёх раундов по одной нерешённой проблеме или без заметного прогресса координатор сообщает о затруднении. Смена исполнителя не обнуляет число попыток.

## Проверка UI через Playwright MCP

Если обычный запуск приложения не удался, тестировщик изучает ошибку и локальные инструкции проекта (`AGENTS.md`, README, документацию запуска и scripts целевого приложения). Затем пробует применимый документированный способ запуска в рамках своих разрешений, проверяет готовность сервера и продолжает UI-проверку. Если запуск требует изменения исходников, зависимостей или конфигурации либо доступные способы не помогли, он передаёт координатору `blocked` с использованными инструкциями, командами и результатами попыток.

Тестировщик проверяет изменённые сценарии и затронутые соседние действия. По применимости проверяются desktop/mobile viewport, вёрстка, формы, переходы, keyboard focus, состояния loading/empty/error/success, ошибки console и неуспешные сетевые запросы. Визуальные изменения проверяются просмотром скриншотов; одной успешной загрузки страницы недостаточно.

Результаты сохраняются в `ui-testing.md`: проверенная версия кода, URL, маршруты, viewport, ожидаемые и фактические результаты, статусы `passed` / `failed` / `blocked`, доказательства и ограничения. Дефекты получают стабильные ID и шаги воспроизведения.

Если Playwright MCP, приложение, авторизация или тестовые данные недоступны, проверка получает `blocked`. Чтение кода и unit-тесты не заменяют проверку UI в браузере. При изменении UI завершение требует успешной обязательной проверки `playwright-ui` либо вашего явного исключения. Результат старой версии кода нельзя автоматически считать актуальным.


## Практики Superpowers внутри flow

В frontend-flow встроены выбранные практики Superpowers. Отдельная установка плагина для этого процесса не требуется. Запуск — через `@FF` или `$frontend-flow`; второй процесс управления агентами не запускается. Автоматические обновления Superpowers не меняют эти локальные правила.

- **Диагностика:** перед исправлением разработчик или багфиксер воспроизводит проблему, собирает факты и проверяет конкретную гипотезу причины. Неподтверждённые исправления не накапливаются.
- **TDD по характеру задачи:** для значимых изменений логики и воспроизводимых ошибок при наличии подходящих тестовых инструментов сначала проверяется падающий тест поведения, затем исправление и успешный тест. Ошибка настройки теста не считается доказательством воспроизведения бага.
- **Небольшие UI-правки:** для текста и стилей с низким риском используются визуальные/интерактивные и подходящие существующие проверки. Формальные тесты CSS-значений не обязательны. Уже написанный корректный код не удаляется ради соблюдения порядка TDD.
- **Проверка требований и кода:** один независимый ревьюер сопоставляет критерии готовности с реализацией и доказательствами, затем проверяет дефекты. Для нескольких пакетов работ оценивается и их взаимодействие.
- **Доказательства результата:** в отчёте указываются реальные команды, результаты и ограничения. Успешный lint не заменяет сборку или проверку интерфейса. Отсутствующая проверка не объявляется успешной; актуальные результаты повторно используются, пока код и окружение не изменились.

Текущая рабочая копия используется, если подходит задаче; отдельный Git worktree создаётся при необходимости изоляции. Незакоммиченные изменения не считаются автоматически перенесёнными в него. Существующие ошибки проверок отделяются от новых регрессий.

Если одновременно явно запросить полный Superpowers и frontend-flow, несовместимые требования нужно разрешить до затронутого этапа. Эта адаптация не обещает выполнение всех правил исходного плагина.

## Продолжение работы и результаты

План, состояние, отчёт реализации и исправлений, отчёт UI-тестирования при необходимости, ревью и итоговые тексты обычно сохраняются в `.frontend-flow/<task-id>/` внутри проекта; если проект требует другое место, координатор указывает фактический путь. Эти служебные файлы не должны попадать в коммит с реализацией.

Для продолжения в чате нужного проекта напишите:

> Продолжи $frontend-flow для [задача или путь к её артефактам]. Используй сохранённые план и состояние; проверь прежнее согласование по переписке.

Сохранённый план не запускает новое планирование, если остаётся актуальным. Если подтверждение согласования недоступно, координатор попросит подтвердить существующий план. Изменения кода после финального ревью требуют проверки этих изменений и обновления итоговых текстов. Для UI заново проверяется применимость доказательств к текущей версии кода; затронутые сценарии выполняются повторно.

## Завершение и очистка

После подготовки окончательных текстов коммита/MR и успешного `check-done` удаляются `plan.md` и временные копии плана — без ожидания подтверждения завершения. Остальные служебные файлы сохраняются до подтверждения завершения. Координатор показывает полные тексты коммита и MR в чате и спрашивает: «Завершаем задачу и удаляем её служебные файлы .frontend-flow?» Согласование плана или разрешение на реализацию не заменяет подтверждение завершения.

После подтверждения выполняется только очистка временных файлов этой задачи, включая созданные вне `.frontend-flow`. Повторные проверки diff, snapshot, хешей, тесты, ревью и `check-done` на этом этапе не запускаются. Исходники, чужие файлы и итоговые пользовательские результаты сохраняются; тексты коммита и MR остаются в чате. Отсутствие уже удалённого плана не запускает повторные проверки.

## Отдельный вызов

Вне flow доступны **только ревьюер и автор**. Пишите обычным сообщением в задаче нужного проекта — Codex делегирует указанному агенту без запуска остальных этапов.

**Ревью:**

> Вызови агента frontend_reviewer отдельно, без frontend-flow. Проверь незакоммиченные изменения. Верни ошибки с файлами, строками и приоритетами. Код не меняй.

Можно указать конкретный коммит или сравнение веток. План и артефакты flow не требуются.

**Описание MR:**

> Вызови агента frontend_writer отдельно, без frontend-flow. По незакоммиченным изменениям подготовь заголовок и описание MR по шаблону проекта. Ничего не публикуй.

**Сообщение коммита:**

> Вызови агента frontend_writer отдельно. Подготовь сообщение коммита по staged-изменениям. Сам коммит не создавай.

Можно запросить оба текста сразу. Для черновика успешные тесты и ревью не обязательны; отсутствующие результаты автор обозначит честно. В полном flow проверка перед написанием текстов остаётся обязательной.

## Стиль ответов

- Отвечай на русском, если пользователь явно не попросил другой язык. Технические термины сохраняй.
- Начинай с ответа или результата. Затем добавляй только необходимые причины и следующие действия.
- Убирай приветствия, вступления, повторения, церемониальные фразы и заключения без новой информации. Не добавляй искусственную речь «пещерного человека».
- Используй короткие, понятные предложения и обычные слова. Не придумывай сокращения. Ясность важнее краткости.
- Сохраняй все существенные факты, отрицания, ограничения, числа и единицы измерения.
- При показе изменения существующего кода обычно показывай изменённые строки с небольшим контекстом. Полный файл показывай по запросу, для нового файла или если изменена большая часть файла.
- Не сокращай и не перефразируй код, команды, пути, имена API и сообщения об ошибках. Не сокращай существующие комментарии при правках файлов.
- Если пользователь просит подробную инструкцию, объяснение или полный пример, дай необходимую полноту: все шаги, команды, проверки и значимые условия. Экономь на лишних словах, а не на содержании.
- Предупреждения о безопасности, вопросы пользователю и неоднозначные инструкции формулируй полными понятными предложениями. Если пользователь не понял ответ, объясни подробнее.

## Общие правила

Все агенты защищают `.env` и секреты, соблюдают разрешения и сохраняют чужие изменения. Передают короткий контекст и переиспользуют актуальные проверки. Коммиты, публикация MR и отправка сообщений требуют соответствующей инструкции пользователя.

Текущие модели и уровни усилия указаны в таблице; их нельзя молча подменять. После обновления инструкций ролей начните новый чат нужного проекта. Если он всё ещё показывает старую конфигурацию, перезапустите Codex. Качество и экономию обновлённого процесса стоит оценивать на реальной работе.
